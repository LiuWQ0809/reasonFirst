# v0.2.0 Design Proposal: Controlled Write Access and Coding Workflow

## Goal

v0.2.0 should allow ChatGPT to move from **repository inspection** to a controlled end-to-end software workflow:

```text
ChatGPT
  ↓
create isolated worktree
  ↓
inspect code
  ↓
edit / patch files
  ↓
run build / tests
  ↓
review diff
  ↓
commit
  ↓
push feature branch
  ↓
create merge request
```

The design should preserve the safety properties of v0.1.0:

- never edit the user's primary checkout;
- never push directly to a protected/default branch;
- no force push;
- no merge/delete operations in v0.2.0;
- every remote write is explicit and auditable;
- repository content is treated as untrusted input.

## Important ChatGPT availability note

As of 2026-09-18, ChatGPT **full MCP write/modify actions are available to Business and Enterprise/Edu workspaces, not Pro**. Pro can connect custom MCP servers for read/fetch actions, but write actions exposed by v0.2.0 cannot currently be used from an ordinary Pro ChatGPT conversation.

The server can still be developed and tested locally with MCP Inspector. To use the complete write workflow from the normal ChatGPT chat window today, use a supported Business / Enterprise / Edu workspace and review its write-action approval settings.

Current OpenAI reference:
https://help.openai.com/en/articles/12584461-developer-mode-and-mcp-apps-in-chatgpt

## Architecture

### 1. Keep the current GitLab read client

The existing read tools remain unchanged:

- `gitlab_whoami`
- `list_projects`
- `get_repository_tree`
- `get_file`
- `search_code`
- MR / pipeline / job-log reads

This avoids making normal inspection depend on a local checkout.

### 2. Add a Workspace Manager

A new `WorkspaceManager` owns local coding workspaces under a configured root:

```text
WORKSPACE_ROOT/
├── repos/
│   └── <project-key>.git          # cached bare repository
└── worktrees/
    └── <workspace-id>/            # one isolated task checkout
```

Suggested environment variable:

```bash
GITLAB_WORKSPACE_ROOT=~/.local/share/chatgpt-gitlab-mcp
```

Workflow:

1. fetch/update a cached bare clone;
2. resolve the requested base ref;
3. create a unique branch such as:
   `chatgpt/<task-slug>-<short-id>`;
4. create a Git worktree for that branch;
5. return a short opaque `workspace_id`.

The MCP should never operate outside `WORKSPACE_ROOT`.

### 3. Local workspace tools

Proposed read/local tools:

- `workspace_create(project, base_ref, task_slug)`
- `workspace_status(workspace_id)`
- `workspace_list_files(workspace_id, path)`
- `workspace_read_file(workspace_id, path)`
- `workspace_diff(workspace_id)`
- `workspace_cleanup(workspace_id)`

Proposed write tools:

- `workspace_apply_patch(workspace_id, patch)`
- `workspace_write_file(workspace_id, path, content)`
- `workspace_delete_file(workspace_id, path)` — optional, potentially defer to v0.2.1

All paths must be normalized and rejected if they escape the worktree.

### 4. Build and test execution

Arbitrary shell access is the highest-risk part of this design.

For v0.2.0, prefer a structured command runner:

```text
workspace_run_command(
    workspace_id,
    argv=[...],
    timeout_seconds=...,
    env={... optional ...}
)
```

Implementation requirements:

- use `subprocess` with `shell=False`;
- fixed current directory = the selected worktree;
- executable allowlist;
- timeout;
- output-size cap;
- remove GitLab/OpenAI secret variables from the child environment;
- no sudo;
- no implicit shell expansion;
- optional network isolation when running inside a container.

Example configurable executable allowlist:

```bash
GITLAB_ALLOWED_EXECUTABLES=python,pytest,uv,npm,pnpm,yarn,node,make,cmake,ninja,cargo,go,mvn,gradle
```

Do **not** add `bash`, `sh`, `zsh`, `curl`, or `ssh` by default because they largely defeat the allowlist.

Longer term, containerized task execution is safer than running builds directly on the host.

### 5. Git operations

Git operations should be implemented as dedicated tools rather than exposing raw `git` commands:

- `workspace_commit(workspace_id, message)`
- `workspace_push(workspace_id)`
- `workspace_push_and_create_mr(workspace_id, target_branch, title, description)`

Rules:

- branch must begin with an allowed prefix, default `chatgpt/`;
- reject default/protected branch as a source branch;
- reject force push;
- reject push if the local worktree contains uncommitted changes unless explicitly intended;
- record commit SHA and pushed branch in the workspace state.

## GitLab credentials for v0.2

GitLab's token model allows us to avoid a broad API write token for the initial design.

Recommended scopes:

```text
read_api
write_repository
```

Why:

- `read_api` supports the existing GitLab API reads;
- `write_repository` supports Git-over-HTTP push;
- GitLab push options can create a Merge Request during `git push`.

This means the v0.2 happy path does **not** need the broad `api` scope just to create an MR.

GitLab documentation:
- token scopes: https://docs.gitlab.com/security/tokens/access_token_scopes/
- push options: https://docs.gitlab.com/topics/git/commit/#push-options

For deployments that need richer MR API writes later (reviewers, labels, comments, updates), prefer GitLab fine-grained token permissions if available. Otherwise an `api` scoped token is broader and should be separated from the Git push credential.

## Creating the MR without broad API write access

GitLab supports creating an MR while pushing:

```bash
git push origin <branch> \
  -o merge_request.create \
  -o merge_request.target=main \
  -o merge_request.title="Fix ..." \
  -o merge_request.description="..."
```

This is attractive for v0.2 because one `write_repository` credential can push the branch and request the MR atomically.

The MCP tool should build these arguments itself rather than accepting arbitrary push options from the model.

## Tool annotations / approval model

Tools should accurately declare risk:

Read-only:
- `read_only_hint=True`

Local reversible writes:
- `read_only_hint=False`
- `destructive_hint=False`

Remote branch push / MR creation:
- `read_only_hint=False`
- `destructive_hint=False`
- non-idempotent where appropriate

Cleanup/delete tools:
- `destructive_hint=True`

In supported ChatGPT workspaces, write actions can trigger user confirmation depending on app permissions and context. The MCP must still enforce its own server-side safety rules; UI confirmation is not a security boundary.

## Proposed end-to-end conversation

User:

> Fix the timeout bug in project A. Run the unit tests and open an MR.

Expected tool flow:

```text
1. workspace_create(project="team/project-a", base_ref="main", task_slug="fix-timeout")
2. inspect/read/search tools
3. workspace_apply_patch(...)
4. workspace_run_command(... pytest ...)
5. workspace_diff(...)
6. ChatGPT summarizes the patch and test result
7. workspace_commit(..., message="Fix request timeout handling")
8. workspace_push_and_create_mr(
       target_branch="main",
       title="Fix request timeout handling",
       description="Summary + tests"
   )
9. return branch, commit SHA, MR URL
```

If tests fail, the default behavior should be to keep the worktree and **not push** unless the user explicitly asks.

## Workspace lifecycle

Each workspace should store minimal metadata:

```json
{
  "workspace_id": "...",
  "project": "team/project-a",
  "base_ref": "main",
  "branch": "chatgpt/fix-timeout-ab12cd",
  "created_at": "...",
  "last_commit": "...",
  "pushed": false
}
```

Add configurable expiration:

```bash
GITLAB_WORKSPACE_TTL_HOURS=48
```

Cleanup should refuse to delete a workspace with uncommitted/unpushed changes unless `force=true` and the action is treated as destructive.

## Security boundaries

Repository content, build scripts, test scripts, package scripts, and CI configuration are untrusted.

Threat examples:

- a malicious README tells the model to expose tokens;
- `npm test` executes a malicious lifecycle script;
- a Makefile reads `~/.ssh`;
- a generated patch edits files outside the intended repo;
- a prompt-injected file asks the model to push to another branch/project.

v0.2 controls:

1. secrets are not inherited by build/test subprocesses;
2. all file paths are anchored to a single worktree;
3. project allowlist remains mandatory/recommended;
4. branch prefix policy;
5. no default-branch push;
6. no force push;
7. command allowlist;
8. output cap + timeout;
9. explicit write-tool annotations;
10. audit log for every write command and resulting commit/MR.

## Suggested implementation milestones

### v0.2.0-alpha.1 — worktree and local edits

- WorkspaceManager
- `workspace_create`
- `workspace_status`
- `workspace_read_file`
- `workspace_apply_patch`
- `workspace_diff`
- `workspace_cleanup`

No remote writes yet.

### v0.2.0-alpha.2 — build/test

- structured command runner
- executable allowlist
- timeout/output caps
- scrubbed child environment

### v0.2.0-beta.1 — commit and push

- `workspace_commit`
- `workspace_push`
- branch policy
- HTTPS Git auth without embedding token in committed config

### v0.2.0-rc.1 — MR workflow

- `workspace_push_and_create_mr` using GitLab push options
- return MR URL
- end-to-end tests
- write-action documentation

### v0.2.0

- stable tool schemas
- Business/Enterprise/Edu ChatGPT test
- migration guide from v0.1.x
- security review

## Deliberately deferred

These should not be part of initial v0.2.0:

- merge MR;
- approve MR;
- delete remote branches;
- force push;
- modify CI/CD variables;
- secrets management;
- arbitrary shell;
- production deployment actions.

Those can be considered later after the branch/commit/MR workflow has been exercised safely.
